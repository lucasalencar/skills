# Readability

- Premature optimizations that trade readability for performance.
- Long functions that combine multiple conceptual steps or branches. Identify cohesive stages that can become helper functions with intent-revealing names, so the top-level function reads as an outline of the operation. Flag this especially when a reader must keep state from earlier branches in mind to understand later ones; do not suggest mechanical extractions that merely move lines without clarifying responsibility or control flow.
- Deeply nested conditionals or names that describe implementation rather than intent. Suggest extractions, guard clauses, or renames that let a reader understand what the code does without tracing through how it does it.
- Names as semantic contracts. For changed or newly introduced functions and variables, compare the name with the implementation and the relevant callers or surrounding flow. Focus on names that conceal or misstate the domain responsibility, input or output shape, boolean polarity, mutation, side effect, time scope, or error behavior. Report a finding when the mismatch can plausibly lead a reader to use, maintain, or review the code under the wrong mental model. State the name, the behavior it actually represents, and an intent-revealing direction for the name. Preserve conventional or adequately clear local names; this is not a style pass.
- For changed web or front-end UI components, look for a component that combines independently meaningful visual regions, interaction flows, or state responsibilities such that its structure no longer explains the screen. Report an extraction only when there is a coherent component boundary with a clear responsibility and ownership of inputs or state; identify that boundary and the concrete readability or maintenance cost it resolves. Keep focused markup and tightly coupled behavior together when extraction would merely move template code or create a forwarding wrapper.
