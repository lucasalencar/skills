# Test quality

- Assertions that only exercise mock behavior (e.g. verifying that a mock was called, or asserting on values the test itself injected) — these give false confidence because they test the test setup, not the code under test.
- Missing coverage for important scenarios: check whether the tests cover only the happy path, or also exercise meaningful edge cases (empty inputs, boundary values, error conditions). Flag gaps that are likely to hide real bugs, but avoid demanding exhaustive coverage of unlikely or trivial variations.
- **Dependency contracts:** Trace important behavior affected by the change across its dependencies and consumers, including callers and tests outside the diff. Identify concrete assumptions about shared contracts, such as response or persisted data formats, fields, types, and error semantics. For each material assumption, inspect the relevant tests and fixtures to determine whether an incompatible change would make a test fail. Check both directions: a changed consumer's dependencies and a changed producer's downstream consumers.
- Examine whether mocks and fixtures preserve evidence of the real contract. A test that invents both sides of an interaction, or only checks that a mock was called, may keep passing after the actual dependency changes. Look for tests that exercise the real boundary or validate against an authoritative contract; account for equivalent protection elsewhere in the suite.
- Report an actionable coverage gap when a specific, consequential contract assumption lacks such protection. Cite the consumer and dependency contract or producer, and the relevant test or fixture when available; describe a concrete incompatible change, the behavior it would break, and why existing tests would not catch it. Recommend a test at the appropriate boundary. Distinguish an unverified contract or test suite from an established gap, and do not require tests for every hypothetical dependency change.
